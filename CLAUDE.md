# Project: code-driven motion graphics

## Background
The files in /reference are animated motion graphics made with code, built in an
earlier conversation. They are the starting point for this project. Read them
before proposing anything.

- northern-lights-titles.html: 6 s title sequence, plain JS + SVG, no libraries
- dungeon-roller-trailer.html: 15 s game trailer, Canvas 2D + SVG, no libraries,
  hand-written 3D D20 (projection, painter's algorithm, flat shading)
- dungeon-roller-v2.html: same trailer, die and lighting in Three.js (r128),
  sound synthesized live with Tone.js (14.8.49)

## Core architecture (keep these principles)
1. Everything is a pure function of time `t`. Nothing is carried between frames,
   so scrubbing, replaying and frame-by-frame export all give identical results.
2. Tracks only produce numbers. `track(group, key, start, duration, easing)`
   writes an eased 0..1 value into a `scene` object. Tracks never touch the DOM.
   (The Northern Lights piece is the earlier, simpler form, where tracks still
   write to the page directly.)
3. Painting is separate. A paint step reads `scene` and draws. When several
   tracks affect one property (e.g. gate rises, later slams), paint combines them.
4. Layers: WebGL/Canvas for the world, a 2D canvas for particles, HTML/SVG on
   top for typography and ornaments. Each tool does what it's best at.
5. Randomness is seeded (mulberry32), so particles are deterministic.
6. Sound: continuous layers follow `scene` every frame; one-shot cues fire when
   the playhead crosses their time while playing forward. Scrubbing is silent.
7. Assets are procedural (feTurbulence paper/stone, canvas-drawn textures),
   so pages are single self-contained files.
8. A debug UI ships with every piece: play/pause, scrubber, and timeline lanes
   generated from the same `tracks` array, so the diagram can't drift from the code.

## Motion Studio (the app built on these principles)
Compositions are JSON files in `compositions/`; the app in `app/` plays, edits and
exports them. The user prompts Claude Code; Claude Code writes the JSON.

- `app/engine/`: `timeline.js` (compile → tracks, evaluate(t) → scene, resolve →
  final values), `render.js` (paintFrame), `elements/*.js` (one module per layer
  type: `props` schema + `paint`). Pure ES modules, no build step; `compile()` also
  runs in Node.
- `app/editor/`: the editor UI (store with undo, inspector, layers, timeline,
  stage handle, exporter). `server.js`: zero-dependency Node server, live reload.
- `docs/composition-format.md`: the format reference. Its prop tables are
  generated by `node tools/gen-docs.mjs`; rerun it after changing an element's props.
- One deliberate difference from principle 4: in the app everything (text too)
  paints into ONE canvas, because a video encoder only takes pixels.
- Combining animations on one prop: before the first starts, hold its `from`;
  each moves from its `from` (or the current value) to its `to`; waves add on top.

### Making a composition from a prompt
1. Read `docs/composition-format.md` (units: positions % of frame, lengths % of
   frame width, times in seconds). Look at an existing composition for style.
2. Write `compositions/<name>.json`: a `notes` field restating the prompt, labels
   on layers so the timeline reads like a storyboard, fonts listed in `fonts`.
3. `node tools/validate.mjs compositions/<name>.json` until it passes.
4. Start the server (`node server.js &`), then render key moments:
   `node tools/render-frames.mjs <name> 0.5 2 4 … --width 1440` and LOOK at them.
   Fix and re-render until each beat reads clearly.
5. Optionally `node tools/export.mjs <name>` → `exports/<name>.mp4`, and check it
   with `ffprobe` (frame count = duration × fps).
6. If the prompt needs something the layer types can't do, add an element module
   in `app/engine/elements/`, register it in `elements/index.js`, regenerate the
   docs, and say so in the report.

When the user edits in the UI and saves, the JSON on disk is the truth: read it
again before changing anything. Keep edits small and targeted so the user's
tweaks survive.
